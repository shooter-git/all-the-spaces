# Contributing

Thanks for helping. Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md). A few
ground rules keep the project safe and self-hostable for everyone:

- **Free and open source only.** New dependencies must use a permissive licence (checked in CI by
  `tools/check-licenses.mjs`). Assets must be CC0 or similar.
- **No paid services.** Everything must work on a single self-hosted server.
- **Nothing environment-specific.** Never commit secrets, real photos, floor plans or anything about a
  real place or person. CI scans for secrets.
- **Plain language in the UI.** Architects may not be technical. Avoid jargon; explain what happens.
- **Mobile first.** Every screen must work on a phone in portrait and landscape.
- **AI compliance.** Read [docs/compliance.md](docs/compliance.md) before touching the Studio,
  sandboxes or anything that runs an AI assistant.

## Database migrations

Change the schema in `packages/db/src/schema/`, then run `pnpm --filter @ats/db db:generate` for a
migration. **Until the first tagged release, migrations may be squashed freely** (all of them
regenerated as one `0000_init`); after a squash, a development database either starts afresh or
marks the new migration as applied (see [docs/development.md](docs/development.md#database-migrations)).
Drizzle can't declare a foreign key `DEFERRABLE`, so the six that form cycles (a space or creation
and its current version, a build and its version or workspace) have `DEFERRABLE INITIALLY DEFERRED`
added by hand in `0000_init.sql`; a squash must add it again (an integration test checks).
**After the first tagged release they are append-only:** never edit, reorder or delete one that has
been released, because servers out there have already run it. Fix mistakes with a new migration.

Before opening a pull request run `pnpm lint`, `pnpm typecheck` and `pnpm test`. Changes to
`deploy/` should also pass `deploy/install/test/run.sh`.

## Versioning

**The platform has one version: its release tag.** A release is a git tag `vMAJOR.MINOR.PATCH`.
Pushing one runs the release workflow (`.github/workflows/release.yml`), which builds and signs the
images, tests installing, updating and rolling back with them, and publishes the GitHub release
with the installer. A tag with a suffix (`v1.0.0-rc1`) becomes a prerelease, which new installs and
`ats-admin update` never pick (they fetch the latest release). The release notes are generated by
GitHub (`gh release create --generate-notes`): the pull requests merged since the previous tag and
a link to every change, so give pull requests titles that read well in that list. The apps and
internal packages (`@ats/*`) stay at `0.0.0` and are never published: don't bump them.

**The MIT packages have versions of their own**, because creations depend on them:
`@allthespaces/portal` (the SDK), `@allthespaces/bridge-protocol` and `@allthespaces/ats-cli`. Each
published version of a creation records the SDK version it was built with
([docs/protocol-compat.md](docs/protocol-compat.md)). They aren't on npm yet
([docs/licensing.md](docs/licensing.md)), so they ship inside platform releases. Raise a package's
version in the pull request that changes what it gives creations or workspaces: while they're
`0.x`, the patch number for a fix and the minor number for anything new. `SDK_VERSION` follows the
SDK's `package.json`. When the SDK's version changes, add a line to the version history in
[docs/protocol-compat.md](docs/protocol-compat.md#version-history). The protocol's own number
(`PROTOCOL_VERSION`) is separate from the package's version and goes up only when a change can't
be additive, as that page explains.
